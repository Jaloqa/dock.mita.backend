# Expense Groups (Core) Implementation Plan

**Goal:** A "Groups" tool for a registered user who owns the group: members (names), the standard dock.mita categories plus group-specific ones, expenses in any currency paid by one member and split equally (between everyone or some members) or by exact amounts, partial repayments between members in any currency, every entry converted into the group's main currency at the official rate of its date or a manual rate, balances per member with the suggested transfers that settle everyone (also shown in another currency), and a full change history per entry with deleted entries visible and restorable. Groups never touch the owner's accounts, budgets, reports or overview.

**Scope:** Delivery item 3 of the spec is split into two plans. This plan (3a) builds everything above for the owner. Plan 3b (`2026-10-23-groups-share-link.md`, written after this one is merged) adds the share link: anonymous access by token, "who am I", link holders writing entries as the member they picked, rate limiting. Personal accounting (email invites, linking members to accounts, "To confirm", settlement marks) is part 4. This plan already records an actor on every change and resolves a group through one access service, so 3b adds link holders without touching the entry slices.

**Architecture:**
- **Domain** (`Mita.Domain/Groups`): `Group`, `GroupMember`, `GroupCategory`, `GroupExpense` with its `GroupExpenseShare` rows, `GroupRepayment`, `GroupEntryEvent` (one row per change, with the actor and the full entry state after the change), plus the pure algorithms `MinorAllocation` (largest-remainder split of minor units), `GroupExpenseSplits` and `GroupSettlement` (suggested transfers).
- **Persistence:** one migration `Groups` with seven tables. Nothing joins `account_movements`; no personal query reads group tables.
- **API:** a `Groups` feature under `/v1/groups` (groups, members, categories, expenses, repayments, history, restore, balances). `Common/Groups` holds `GroupScope` + `GroupAccess` (owner resolution now, link resolution in 3b), DTOs, queries, input validators, writers, pricing and event recording. Entry and read commands carry a `GroupScope`; owner-only commands (group, members) carry the group id.
- **Frontend:** a `groups` feature: `/tools/groups` (list, new group) and `/tools/groups/[id]` (summary, balances, expenses, repayments, members, settings, history, deleted view). The group page talks to the API through a `GroupScope` (`{ kind: 'owner', groupId }`) provided to its components, so 3b renders the same components for a link. The mock backend implements the same rules.

**Tech Stack:** Backend: .NET 10, EF Core migrations (Npgsql, `text[]` and `jsonb` columns), MediatR 12.5.0, FluentValidation, xUnit v3, Shouldly, Moq, Bogus, Testcontainers. Frontend: Nuxt 4, PrimeVue 4.5 (`Dialog`, `SelectButton`, `Select`, `Checkbox`, `DatePicker`, `InputNumber`, `AutoComplete`), TanStack Query (`useQuery`, `useInfiniteQuery`, `useMutation`), Vuelidate, bun:test, Playwright 1.64.1. No new packages in either repo.

**Spec:** `dock.mita.frontend/docs/superpowers/specs/2026-10-22-tools-design.md`: "Groups" (Ownership, Members, Only the owner changes the group itself except invites and the link, Authorship, Expense fields, Split, Repayment, Currencies, Balances), calls "Standard category keys" (see Decisions) and "History", "Left to builder" (data model, settlement algorithm, rounding of splits, UI layout, mock coverage), Anti-goals "Inflated spending" and "Lost entries", constraints "Languages", "Contract", "Money", Delivery item 3. Also binding: both repos' project guides and `docs/STACK.md`, backend `docs/api-contract.md`, the rate rules of `docs/superpowers/plans/2026-10-22-currency-list.md` and the structure of `docs/superpowers/plans/2026-10-23-tools-and-debts.md`. Code to reuse: backend `Common/{Rates/RateTable,Rates/ManualRate,Tags/TagNames,Wire/JsonValues,Money/CurrencyWire,Time/UtcCalendar,Paging,Debts/DebtLocks}`, `Domain/{Money/*,Categories/StarterCategories}`, `Features/{Debts,Overview}`; frontend `app/shared/{api/invalidation.ts,money/money.ts,rates/useRates.ts,components/*}`, `app/features/{tools,debts}`, `app/features/transactions/components/TransactionTagField.vue` (pattern only, not imported), `mocks/{db,rates,validation,paginate,errors,debts}.ts`, `mocks/handlers/debts.ts`, `mocks/seed/*`.

| Topic | Decision | Cost if wrong |
|---|---|---|
| Plan split | 3a (this plan: groups for the owner, both repos, own PRs), then 3b (share link, own PRs) | The share link ships in a second pair of PRs |
| Access in 3a | Only the owner (the user who created the group) reads or changes it. Every route requires the user policy; an unknown or foreign group id answers 404, as does an entry id of another group | None |
| Standard category keys | A group expense stores the standard key of a starter expense category (`groceries`, `transport`, `housing`, `cafes`, `health`, `shopping`, `leisure`, `gifts`, `other`; never `transfer`) or a group category id. The key column on personal `categories` and its migration deriving keys from names in the four locales are deferred to part 4, the only consumer (suggestions on confirmation) | None for part 3; part 4 adds the column |
| Storage | Own tables `groups`, `group_members`, `group_categories`, `group_expenses`, `group_expense_shares`, `group_repayments`, `group_entry_events`; no account legs, no transactions | None (anti-goal "Inflated spending") |
| Members | Names 1-40 characters after trimming, no control characters, unique per group case-insensitively (`validation.memberNameTaken`), at most 50 (`validation.tooManyMembers`); creation takes 1 to 50 names, positions in request order; new members go last. A member is "in use" when any expense (payer or share), repayment (either side) or history event (actor) references it, deleted entries included: it can be renamed but not removed (`memberId: ["validation.memberInUse"]`) | A member added by mistake and used in a deleted entry stays in the list |
| Main currency | Any of the 148 currencies. It can change only while the group has no expense or repayment, deleted ones included (`currency: ["validation.groupCurrencyLocked"]`) | A group created in the wrong currency must be recreated once it has entries |
| Entry conversion | `rate` = entry currency → main currency: 1 for the same currency (a sent `rate` is validated, then ignored, `rateManual` false); the manual `rate` rounded by the rate rule (`rateManual` true); otherwise the stored rate of the entry `date` (latest on or before) under the 30-day staleness rule of writes: missing or stale → 503 `rates.unavailable`, nothing written. `groupAmount` = converted, half away from zero; 0 → `rate: ["validation.positiveAmount"]`, above 100 000 000 000 → `rate: ["validation.invalidValue"]`. Stored, never re-priced except by an edit; `PUT` without `rate` re-prices at the date's rate. The dialog resends the stored rate only when it was manual | An entry in a currency NBP stopped publishing needs a manual rate after 30 days |
| Split | `split` omitted or null: equal between all current members. `{ mode: 'equal', memberIds }`: equal between those members. `{ mode: 'exact', shares: [{ memberId, amount }] }`: exact amounts in the expense currency, each 1..amount, summing to `amount` (`split: ["validation.splitMismatch"]`). Shapes: non-empty arrays of at most 50 distinct members, otherwise `split: ["validation.invalidValue"]`; a member id that is not a GUID or not in the group is `split: ["validation.unknownMember"]`. Shares are stored per member, so adding or removing members never changes a past entry | None |
| Rounding | Largest remainder (`MinorAllocation`). Equal split: the expense amount is allocated with weight 1 per member; group amounts: the expense `groupAmount` is allocated by the share amounts. Ties of the remainder go to the payer when the payer shares, then to the split members in member order. So the shares of every expense add up exactly to its amount and to its `groupAmount`, and balances always sum to 0 | None |
| Categories | The group lists the 9 standard keys (in starter order, localised by the client) then its own categories (creation order). `categoryId` on an expense is a standard key or the id of a category of this group; omitted → `other`; anything else → `validation.unknownCategory`. Group category names 1-40, unique per group case-insensitively and not equal to a standard category's name in any of the four locales (`validation.categoryNameTaken`), at most 100 (`validation.tooManyCategories`). No rename or delete in part 3 | A mistyped group category stays |
| Expense fields | `payerId`, `amount`, `currency`, `date` (≤ today + 1 year), `categoryId`, `tags` (transaction tag rules: names 1-30, at most 10 distinct case-insensitively, stored as entered after dedup), `description` (≤ 100 after trimming, `validation.titleTooLong`, null when blank), `rate`, `split` | None |
| Repayment fields | `fromMemberId` → `toMemberId` (different: `toMemberId: ["validation.sameMember"]`), `amount`, `currency`, `date`, `rate`, `note` (≤ 200, `validation.noteTooLong`). Any amount; partial repayments are normal and may exceed what is owed (it then flips the balance) | A typo can make the receiver owe the payer; visible in balances and history |
| Delete and restore | `DELETE` is soft (`deletedAt`): the entry leaves balances and totals, is listed with `?deleted=true` and comes back unchanged with `POST .../restore`. A deleted entry cannot be edited (404, restore first); deleting a deleted one and restoring a live one answer 404. Rows are removed only with the whole group | None (anti-goal "Lost entries") |
| History | Every create, update, delete and restore of an expense or repayment appends a `group_entry_events` row: action, time, actor and the full entry state after the action (`jsonb`). `GET .../history` lists them newest first; the client shows what changed between consecutive states | None |
| Actors | An event stores `ActorUserId` (the owner) or, from 3b on, `ActorMemberId` (a link holder's pick). Wire `GroupActor = { kind: 'owner' \| 'member', memberId, name }`: the owner's current user name, or the member's current name. `createdBy`/`createdAt` come from the first event, `updatedBy`/`updatedAt` from the newest later event (null when never changed) | None |
| Balances | Per member over live entries, in the main currency: `paid` (expenses paid), `share` (expense shares), `sent` and `received` (repayments), `balance = paid - share + sent - received`; positive = the others owe the member. `total` = sum of live expense `groupAmount`. Members in member order | None |
| Suggested transfers | `GroupSettlement`: first every debtor (member order) pays a creditor whose balance is the exact opposite (first in member order); then repeatedly the largest debtor pays the largest creditor the smaller of the two (ties by member order). At most one transfer fewer than the members with a non-zero balance; exact pairs avoid the common greedy extra transfer. "Who owes whom" is shown as these transfers (no pairwise ledger) | In rare cases one transfer more than the theoretical minimum |
| Another currency | `GET .../balances?currency=X` converts every figure (paid, share, sent, received, balance, total, transfer amounts) separately from the main currency at today's latest stored rate whatever its age (a read), half away from zero; 503 when X never had a rate. Transfers are computed in the main currency first. Converted figures can miss a zero sum by a few minor units | Displayed balances may not sum to exactly 0 in the view currency |
| Concurrency | Entry writes lock the group row `FOR SHARE` and the edited entry `FOR UPDATE`; member changes, group update and delete lock the group `FOR UPDATE`. No optimistic concurrency token: the later of two simultaneous edits wins and the earlier stays visible and re-applicable in the history | Two people editing the same expense at the same moment are not warned |
| Lists | `GET /v1/groups`: newest created first. Expense and repayment lists: `date`, creation time, `id`, all descending; history: newest first. Default and maximum `pageSize` 100; the page loads 100 and offers "Show more" (infinite query) | None |
| Navigation and UI | The Tools hub lists Groups first, then Debts (spec order). `/tools/groups`: group cards, "New group". `/tools/groups/[id]`: summary cards, Balances (with "Show in" currency and suggested transfers, each with "Record"), Expenses and Repayments sections each with an Active / Deleted switch, dialogs for expenses, repayments, members, group settings and history | None |

Oleh has none. `MockState.version` becomes 4 | Developer mock data resets once |

## Review Focus

- Balances must sum to exactly 0 in the main currency for any mix of equal, subset and exact splits, currencies and member counts (shares of every expense add up to its amount and its `groupAmount`). Pinned in Task 1 (`MinorAllocationTests.Should_KeepTheTotal_ForRandomInputs`, `GroupExpenseTests`) and Task 7 (`Should_SumToZero_ForManyEntries`).
- Editing, deleting or restoring an entry must never lose what it was: every change appends an event with its actor and full state, a deleted entry leaves balances and comes back unchanged on restore. Pinned in Task 5 (`Should_DeleteAndRestoreExpense`, `Should_UpdateExpense_AndRecordTheChange`), Task 6 and Task 14 (E2E).
- Members changing must never change past entries: adding a member leaves existing shares and balances as they were; a member referenced by any entry, deleted or not, cannot be removed. Pinned in Task 3 (`Should_KeepExistingShares_When_MemberAdded`, `Should_RemoveMember_OnlyWhenUnused`).
- A cross-currency entry must never be written with a stale or invented rate: 503 unless a manual rate is sent; an edit keeps a manual rate only when the dialog resends it, and re-prices at the new date otherwise. Pinned in Task 4 (`Should_Return503_When_ExpenseRateIsStale`) and Task 5 (`Should_RepriceOnEdit_UnlessRateWasManual`), Task 12 (E2E manual rate).
- Another user's group and its entries must be unreachable on every route, and an entry id of another group in the path must answer 404; groups never change personal totals. Pinned in Tasks 2-7 (`Should_Return404_When_GroupUnknownOrForeign`, `Should_Return404_ForEntriesOfAnotherGroup`) and Task 4 (`Should_NotTouchPersonalData`).
